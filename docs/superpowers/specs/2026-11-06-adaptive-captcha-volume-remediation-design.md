# 北大法宝批量采集低请求量修复设计

- **状态**：已确认设计，等待用户审阅
- **目标版本**：Windows 0.2.5
- **基线**：GitHub `origin/main`（0.2.4）
- **范围**：单篇采集、批量采集、年份筛选、验证码恢复、任务断点、批次下载与本地处理衔接

## 1. 背景

Windows 0.2.4 在“中央 + 地方”且选择较长年份区间时，会明显增加
北大法宝的检索次数。以 1 个关键词、中央和地方、1949—2026 为例，
当前流程会先做 2 次“全部年份”检索，再为 2 个子库的 78 个年份分别
提交完整关键词检索，理论上产生 158 次检索提交。

当前每次年份检索都会重新进入检索页、设置关键词和检索字段、选择子库并
提交完整表单。该行为不仅增加耗时，也显著提高触发平台验证码的概率。

## 2. 目标

1. 在正常场景下，每个关键词在每个子库只提交一次关键词检索。
2. 年份切换优先复用同一个检索结果会话，不重复提交完整关键词表单。
3. 优先一次完成整个年份区间；只有网站结果窗口不足时才进行必要的自动分片。
4. C+ 阶段全程自动执行，除登录和验证码外不要求人工确认。
5. 到达物理采集边界后保存完整断点，转入 A 阶段，由用户确认是否继续补采剩余部分。
6. A 阶段只处理未完成年份或省份，不重新扫描已完成数据。
7. 下载和本地数据处理尽可能流水线执行，避免下载完成后才集中处理。

## 3. 非目标

- 不识别、破解、外推或绕过验证码、登录和机构额度。
- 不通过反检测参数、代理轮换或伪造用户行为规避平台风控。
- 不改变“标题 + 精确”“全文 + 精确”等既有检索语义。
- 不修改中央与地方子库分别检索的边界。
- 不把多关键词合并成一个关键词，以免改变召回语义。
- 不并发操作多个北大法宝浏览器任务。

## 4. 已确认的根因

1. `expand_search_combinations_for_year_windows()` 会把年份区间展开成
   每个年份一个 `SearchCombination`。
2. 单篇和批量管理器随后对每个组合调用完整的
   `PkulawAdapter.search()`。
3. `PkulawAdapter.search()` 每次都会重新设置检索页、关键词、
   检索字段、子库和完整表单，再应用筛选和每页条数。
4. 验证码恢复由 `_with_manual_retry()` 重新执行原动作；如果用户完成
   验证码时原请求其实已经成功，重新执行会再次提交检索。
5. 中央和地方本身会把同一关键词扩展为两个子库范围，使上述问题翻倍。

## 5. 总体设计

采用两阶段混合流程：

```text
C+：单关键词会话快速自动采集
  -> 到达物理采集边界
  -> 保存已完成结果、目标覆盖情况和断点
  -> 显示剩余范围与预计补采量
  -> 用户确认
A：只对未完成范围执行可恢复自动补采
```

### 5.1 C+ 快速自动阶段

对每个关键词、每个目标子库分别建立一个检索会话：

1. 只提交一次关键词表单，首次检索使用“全部年份”。
2. 读取结果总数、可访问页数、可用年份及每个年份的结果数量。
3. 若网站提供稳定的原生年份区间或多年度筛选，直接切换一次目标区间。
4. 若目标范围对应的全部结果都在可访问窗口内：
   - 正常翻页；
   - 根据结果行公布日期在本地筛选目标年份；
   - 按政策稳定身份去重；
   - 直接进入批次下载。
5. 若结果窗口不足：
   - 不重新提交关键词；
   - 在当前结果会话中切换年份筛选；
   - 只补尚不完整的年份；
   - 空年份直接跳过。
6. 中央和地方均完成后，进入下载与本地处理流水线。

年份筛选切换必须保留当前关键词、匹配方式、子库、时效性和每页条数，
不得重新填写或提交完整关键词表单。

### 5.2 本地年份筛选的完整性条件

首次“全部年份”结果只有在以下条件同时满足时才允许在本地筛选：

- 网站声明的总页数能够覆盖全部结果；
- 所有目标年份均可在结果行中识别公布日期；
- 结果身份稳定且能够去重。

若结果行缺少可解析的公布日期，且该行可能落在目标范围内，则该年份
不能仅凭本地筛选视为完成，必须通过年份筛选确认，或报告为待补采。

### 5.3 动态请求节流

不使用“每次固定等待 3 秒”的方案。新增统一的结果操作节流器：

- 两次结果变更操作之间至少间隔 1000 毫秒；
- 若上一操作完成本身已经超过 1000 毫秒，不再额外等待；
- 翻页等待页面实际稳定，不按固定秒数猜测；
- 验证码清除后，在继续原操作前至少等待 10000 毫秒；
- 验证码后的恢复先复核原请求是否已经成功；已成功则直接复用结果；
- 若同一任务在连续 5 次结果操作内第二次出现验证码，停止自动扩张，
  进入 C+ 物理边界，而不是继续制造请求。

### 5.4 物理采集边界

“物理采集边界”定义为以下任意一种情况：

1. 网站报告的实际总页数小于结果量所需页数；
2. 超过网站声明页数后继续翻页只得到重复页或失败页；
3. 当前可选的最细年份或省份范围仍超过网站可访问上限；
4. 中央法规的单年结果超过网站上限，且没有可用的进一步子范围；
5. 连续验证码达到 5.3 节定义的熔断条件。

到达边界时，任务状态进入 `waiting_manual`，错误码使用
`CAPTURE_BOUNDARY_REACHED`。该状态不是失败，已下载文件和已完成扫描
必须保留，任务不得自动重建或从头开始。

检查点至少记录：

```json
{
  "boundary": {
    "reason": "RESULT_WINDOW_TRUNCATED",
    "query": "关键词",
    "library": "central",
    "year": "2020",
    "province": "全部省份",
    "completedPolicyCount": 0,
    "remainingScopeCount": 1,
    "estimatedResultOperations": 0,
    "detectedAt": "ISO-8601"
  },
  "searchActivity": {
    "keywordSubmissions": 2,
    "yearFacetSwitches": 0,
    "captchaWaits": 0
  }
}
```

### 5.5 A 可恢复补采阶段

边界面板向用户显示：

- 已完成政策数量；
- 已完成关键词和子库；
- 尚未完成的年份、省份及对应结果量；
- 预计还需的结果操作次数；
- “继续完整补采”和“保留已完成结果并结束”两个动作。

用户选择“继续完整补采”后：

1. 继续使用同一个任务和同一检查点；
2. 先把模式切换为 A；
3. 只生成未完成分片；
4. 已采政策按稳定身份去重；
5. 已完整批次不得重新下载；
6. 中央和地方均完成后，进入正常的 ZIP、目录和本地处理验收。

### 5.6 分片顺序

未完成部分按以下顺序生成最小必要分片：

1. 年份；
2. 地方法规的省份；
3. 已在表单中指定时效性时，可按时效性类别进一步拆分；
4. 中央法规没有更多可靠子范围时，报告不可再分边界，要求用户缩窄
   年份或关键词。

不得为了减少用户交互而擅自更改标题/全文匹配模式，也不得擅自扩大
或缩小用户选择的年份与省份。

### 5.7 搜索活动可观测性

任务检查点和界面增加统一计数：

- `keywordSubmissions`：完整关键词表单提交次数；
- `yearFacetSwitches`：同一检索会话内的年份筛选切换次数；
- `captchaWaits`：验证码等待次数；
- `completedScopes` / `remainingScopes`；
- `deduplicatedPolicies`：因重复被跳过的政策数。

日志必须记录事件类型、当前关键词、子库、年份、省份和结果窗口状态，
但不得记录 Cookie、账号密码、验证码内容或页面完整正文。

### 5.8 下载与本地处理流水线

在不增加北大法宝网页并发的前提下：

- 每 50 条形成一个原生批量下载批次；
- 一个批次 ZIP 和目录校验通过后，立即加入本地处理队列；
- 浏览器继续顺序下载下一批；
- 本地处理最多使用一个工作单元，避免与浏览器任务争抢磁盘和 CPU；
- 任一本地处理失败只标记对应批次，不回退或重新提交已完成下载。

## 6. 组件边界

### `PkulawAdapter`

- 保留现有完整 `search()`，供单一年份和兼容调用使用；
- 新增“开始关键词会话”和“切换年份筛选”能力；
- 年份筛选切换返回更新后的 `SearchSession`；
- 不在此层决定任务级自动或确认策略。

### 年份计划器

- 只负责根据真实年份数量、结果窗口和目标范围计算完整覆盖情况；
- 输出已完成年份、缺失年份、不可再分边界和预计剩余操作数；
- 不执行浏览器操作，不直接操作任务数据库。

### 单篇与批量任务管理器

- 共享同一套 C+ 边界和 A 回退语义；
- 继续分别负责自身任务生命周期、下载和输出结构；
- 不得复制两套不同的年份覆盖判定。

### 结果操作节流器

- 统一约束完整关键词提交和年份筛选切换；
- 使用可注入时钟，便于确定性测试；
- 不处理验证码内容，只接收验证码事件并应用等待策略。

### 任务工作区

- 在现有任务进度区域显示检索活动计数；
- 到达边界后显示唯一主操作“继续完整补采”和次操作
  “保留已完成结果并结束”；
- 不新增独立任务，不弹出普通浏览器继续按钮来绕过边界。

## 7. 错误与恢复

- 验证码仍可见：保持等待，不继续任何结果操作。
- 验证码已消失但原请求成功：复用原结果，不重新提交。
- 验证码已消失且原请求未完成：经过冷却后只重试原动作。
- 页面结构变化：停止并给出选择器诊断，不自动猜测。
- 结果集身份变化：使用现有扫描日志和隔离机制处理，不覆盖成功批次。
- 边界确认前进程退出：重启后恢复 `CAPTURE_BOUNDARY_REACHED`。
- 边界确认后进程退出：重启后只继续 A 阶段未完成分片。
- 下载成功但本地处理失败：保留原始 ZIP 和目录，批次标记为待处理失败。

## 8. 两阶段交付

### 阶段一：C+ 快速路径

- 一次关键词提交、同会话年份切换；
- 全部年份一次扫描和本地年份筛选；
- 只补缺失年份；
- 动态节流；
- 验证码后复用成功结果；
- 物理边界检测与可恢复检查点；
- 检索活动计数和日志。

阶段一在边界处停止并显示边界信息，不执行大范围自动补采。

### 阶段二：A 可恢复补采

- 边界确认界面；
- 只生成剩余年份和省份；
- 同一任务从断点继续；
- 单年结果继续按省份拆分；
- 下载与本地处理流水线；
- 完整恢复、去重和验收测试。

## 9. 验收标准

1. `1 关键词 + 中央 + 地方 + 较宽年份区间 + 一次可访问完`：
   完整关键词提交次数为 2，不按年份重新提交。
2. 结果窗口足够且发布日期完整：本地年份筛选结果与真实逐年份检索一致。
3. 结果窗口不足：后续操作只做年份筛选切换，不新增关键词表单提交。
4. 空年份不产生检索操作。
5. 已完成年份不会在 A 阶段重复扫描或下载。
6. 中央和地方分别生成正确目录，批量 ZIP 和目录条目数量一致。
7. 边界状态在程序重启后仍可恢复。
8. 用户确认后从同一任务继续，不创建第二个任务。
9. 验证码清除后，若原结果已经成功，关键词提交次数不增加。
10. 动态节流测试不依赖真实等待；使用注入时钟验证 1000 毫秒和
    10000 毫秒规则。
11. 连续验证码达到熔断条件时自动停止扩张并进入边界确认。
12. 不出现自动识别、绕过或提交验证码的代码路径。

## 10. 线上验证边界

自动化测试必须覆盖本地夹具和模拟结果窗口。真实站点验证只执行用户
明确授权的小范围关键词与年份，不主动诱发验证码，不消耗大规模下载额度。
真实验证需要比较优化前后的：

- 完整关键词提交次数；
- 年份筛选切换次数；
- 验证码次数；
- 总耗时；
- 最终政策数量和去重结果。

获得真实站点数据前，不得宣称验证码风险已经按固定比例降低。
