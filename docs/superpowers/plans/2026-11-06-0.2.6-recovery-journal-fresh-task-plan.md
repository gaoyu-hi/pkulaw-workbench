# 北大法宝工作台 0.2.6 恢复与任务生命周期修复计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复验证码恢复后的断点死循环，解耦扫描日志与页数模式，为被动停止任务提供安全的一键新建入口，并统一自动核验“不分组”和原动作恢复语义。

**Architecture:** 在现有 `SearchSession`、任务检查点和浏览器租约之上增加“待执行原动作”与可恢复节流器：每次结果操作先持久化动作身份，验证码解除后先只读核验该动作是否已成功，只有未成功时才冷却后重试一次。扫描日志改用独立的检索宇宙指纹；终端任务通过后端能力评估和脱敏新建种子进入全新任务，不继承任何断点。单篇、批量并行接入同一状态机，但保留各自原有的下载、批次、覆盖和审计边界。

**Tech Stack:** Python 3.14、`unittest`、SQLite 检查点、Electron 45、React 19、TypeScript 7、Vitest 5、Electron `WebContentsView`、DrissionPage。

**Spec:** `D:\北大法宝爬取工具\后续问题记录.md` 中 `ISSUE-20261106-01`、`ISSUE-20261106-02`、原两个 Py 文件采纳要求，以及 `D:\北大法宝爬取工具\修复工作区_0.2.3\docs\PROJECT_STATE.md` 的 0.2.5 基线。

## Root-Cause Evidence

| 现象 | 现有代码证据 | 根因结论 |
|---|---|---|
| 验证码解除后反复重做同一动作 | `single_task.py` 的 `_run_single_adaptive_result_action()` 和 `batch_task.py` 的 `_run_adaptive_result_action()` 都在手动等待后进入下一轮并重新调用 `search()`/`select_year()`；通用 `_with_manual_retry()` 也直接重跑回调 | 恢复点没有持久化“原动作身份”，也没有可靠的原动作只读核验器 |
| 应用重启后验证码次数丢失 | `SearchActionGovernor()` 在任务启动时直接新建；完整快照只在扫描流程末尾组装进 `adaptiveSearch` | 验证码事件、动作窗口、首次验证码位置和熔断状态没有在等待发生时立即落盘 |
| 第二次验证码仍继续扩张 | 熔断判断发生在新启动的 governor 中，且当前 `read_results()` 依赖尚未成功更新的 `current_search_request/session` | 原动作成功但适配器内存状态未完成更新时，代码误判失败并再次提交 |
| 页数模式变化导致旧扫描日志不可复用 | 单篇和批量 `_config_payload()` 都通过 `PageSelection.to_payload()` 把 `pageMode/pageSelection/maxPages` 纳入 `config_fingerprint` | `limit -> last` 改变了检索宇宙哈希，实际结果集并未变化 |
| 被动停止任务只能删除或重启应用 | `TaskDetails` 只有 `task/items/timeline`；`canOpenTaskSettings()` 只允许 `paused`；停止详情没有“新建任务”动作 | 后端未返回恢复/编辑/新建能力，前端也没有脱敏的新建种子 |
| 年份切换后“不分组”失效 | `select_year()` 只点击年份筛选，却通过 `require_ungrouped=True` 和 `require_page_size=True` 要求筛选动作本身同时满足布局；若站点重置分组，代码直接失败而不主动切回“不分组” | “要求结果必须是不分组”不等于“自动执行并核验不分组” |
| 页码/总页数确认过早 | `transition_next_page()` 当前主要用两次稳定采样；原两个 Py 文件在翻页后持续观察直至页码、总页数和列表同时稳定 | 慢加载时容易在复核前进入下一次恢复或回退 |

## Design Decisions

1. **保留同一工作线程，恢复时先看再动。** 进程未退出时不销毁控制器；验证码解除后先读取当前页面并匹配原动作，只读核验为成功就复用结果。只有核验失败才在 10 秒冷却后重试原动作一次。
2. **持久化状态以动作事件为粒度。** 每次关键词提交、年份切换、筛选、翻页、分组或页大小变化都有独立 `actionId` 和 `recoveryEventId`；等待、重试、复用和熔断均立即写检查点。
3. **扫描指纹只描述“检索宇宙”。** 查询、匹配方式、子库、年份、省份、时效性和每页条数进入新指纹；页数模式、最大页数、输出目录和下载格式不进入。旧页数模式指纹以明确白名单兼容，不重写旧 JSONL。
4. **终端任务的新建由后端生成安全种子。** 前端可以复制检索条件，但只能使用后端返回的白名单字段；断点、`searchId`、扫描日志、预览指纹、配置版本和成果登记永远不复制。
5. **结果布局收敛是独立动作链。** 先应用年份/筛选，再检查并点击“不分组”，确认结果刷新，最后检查/应用每页条数。任何一步失败都必须保留可定位的断点，不重复更早的筛选或关键词提交。
6. **最新问题记录覆盖旧节流值。** 0.2.5 的 1000 ms 正常间隔由 0.2.6 调整为约 1500–2500 ms 并加入轻微抖动；验证码清除后的 10 秒冷却和“5 次结果操作内第二次验证码进入边界”保持不变。

## Reference-Py Semantics to Port

| 原两个 Py 文件的做法 | 0.2.6 采用方式 |
|---|---|
| 验证码等待期间保留同一工作线程和页面动作上下文 | 保留 live controller；等待前后都是同一 `PendingSearchAction`，只有进程退出才重建控制器 |
| 解除验证码后先读取当前页，再决定是否重复点击 | 新增 `observe_pending_action()`，只读核验原动作，成功即复用 |
| 原筛选/关键词未成功时重新进入同一核验循环，不从头重跑 | 冷却后只重试原动作一次；更早关键词不再提交 |
| 翻页前先检查是否已在目标页；未到才点击一次 | `next-page` 动作持久化目标页和前一页签名，先观察后点击 |
| 翻页后持续检查页码、总页数和页面状态 | 目标页、请求身份和结果签名连续 3 次稳定后才继续 |
| `input[name="group"][value="2"]` 原生 radio，点击后核验 `checked` | 作为首选选择器，自动点击、等待刷新并核验 `groupingMode=ungrouped` |
| 慢加载时继续观察而不是立即重试 | 先等待稳定采样，超时后才进入受控人工恢复或既有表单回退 |
| 每条约 3 秒、页面操作有 0.5/1/1.5/2.2 秒等稳定等待 | 采用条件等待加慢节奏，不照搬固定睡眠；结果操作 1.5–2.5 秒，跨检索域再增加停顿 |

以下原文件限制明确不移植：2000 年起始规则、20 页结果窗口视为完整、缺少应用重启熔断状态、缺少当前任务修订/永久删除/统一进度/批次原子发布。

## Global Constraints

- 不识别、破解、自动填写、绕过或外传验证码、滑块、登录信息和机构额度信息。
- 单篇与批量共享同一套原动作恢复、验证码熔断、扫描指纹和“不分组”规则。
- 同一时刻只允许一个任务持有内置浏览器租约。
- 验证码解除后至少连续 3 次采样均为无验证码、无登录遮挡，才允许复核原动作。
- 原动作已成功时不得重新提交检索、重做年份筛选或再次点击下一页。
- 原动作未成功时，冷却后只重试原动作一次；不得退回更早的关键词检索。
- 同一动作第二次出现验证码，或在连续 5 次结果操作内第二次出现验证码，必须进入 `CAPTURE_BOUNDARY_REACHED`。
- 验证码等待期间任务保持 `waiting_manual` 或 `waiting_login`，人工等待期间不得落入普通 `stopped`。
- 正常结果操作间隔目标区间为 1500–2500 ms；从一次结果操作完成后计时。
- 不同关键词或不同子库切换时追加约 3–4.5 秒停顿，并使用可注入随机源保证测试确定性。
- `pageMode`、`pageSelection`、`maxPages`、`outputDir`、目录格式和全文格式不得改变扫描宇宙指纹。
- 旧 0.2.5 检查点和扫描日志必须安全升级或继续读取；不得删除、覆盖或伪造已有成功成果。
- “新建任务”不得删除、归档或修改旧任务；新任务必须使用新的 task ID。
- “新建任务”只能复制检索参数与输出目录，不得复制检查点、搜索会话、扫描日志、`searchId`、预览指纹、配置版本或成果记录。
- 旧任务仍持有浏览器租约时，可以在只读意义下打开新表单；启动必须在租约安全释放后通过现有租约门禁。
- 本阶段全部验证只使用离线夹具、单元测试、Vitest、TypeScript 检查和本地 Electron 烟测。

## Review Focus

- 验证码出现时原关键词检索、年份筛选或翻页已经在网站上成功：恢复后必须直接复用，不增加动作提交次数。
- 原动作确实未成功：只能冷却后重试该动作一次，第三次不得继续自动执行。
- 从 `limit` 继续到 `last` 后应用重启：同一结果集必须复用扫描日志，不得报 `SCAN_JOURNAL_CONFIG_MISMATCH`。
- 被动停止任务存在历史租约或成功文件：新表单仍可一次打开，旧成果保留，启动受租约门禁和重复下载提示约束。
- 年份切换令网站重置为默认分组：必须自动点击 `input[name="group"][value="2"]`，等待结果刷新并核验实际选中状态后再继续。

### Task 3: Replace Blind Retry with a Shared Checkpointed Action Runner

**Files:**
- Modify: `engine/pkulaw_engine/search_recovery.py`
- Modify: `engine/pkulaw_engine/single_task.py`
- Modify: `engine/pkulaw_engine/batch_task.py`

- Test: `engine/tests/test_adaptive_single_task.py`
- Test: `engine/tests/test_adaptive_batch_task.py`

**Interfaces:**
- Consumes: Task 1 recovery model, Task 2 `observe_pending_action()`, live `TaskControl`.
- Produces:
  - `CheckpointedActionResultRunner(store, task_id, governor)`
  - `run(action, *, execute, observe, wait_for_manual) -> dict[str, Any]`
  - Task checkpoint key `searchRecovery`
  - `manual_wait_reason` that includes action kind, query, library, year and attempt count.

Required state transitions:

```text
normal:
  persist prepared
  -> execute once
  -> persist completed

CAPTCHA:
  persist waiting + governor snapshot
  -> keep same controller and wait
  -> after valid recovery token: observe only
  -> success: persist reused, return current state
```
